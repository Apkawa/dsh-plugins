### DSH_HOME mechanics (from `dsh/` checkout, read-only; HEAD a66e470204 = 0.1.2-rc.1)

- `dsh/packages/boot/home-paths/src/index.ts`: `DSH_HOME_ENV = 'DSH_HOME'`, `DSH_AGENTS_HOME_ENV = 'DSH_AGENTS_HOME'`, `DSH_HOME_DIR_NAME = '.dsh'`, `AGENTS_HOME_DIR_NAME = '.agents'`. `resolveDshHome()`: configured path > non-blank `$DSH_HOME` > `~/.dsh`.
- `dsh/packages/boot/app-boot/src/profile.ts`: `resolveProfileDir(name, home?)` → `<home>/profiles/<name>` (flat `PROFILES_DIR = 'profiles'`).
- Shipped web profile template: `PROFILE_TEMPLATES.web = { bundles: ['@deepseek-ai/dsh-base', '@deepseek-ai/dsh-web-app'], patchReload: 'live' }`.
- `initProfile(dir, bundles, patchReload)` writes (skips existing files):
  - `package.json`: `{ name: 'dsh-profile-<basename>', private: true, dependencies: {}, dsh: { profile: { bundles, patchReload } } }`
  - `cordis.patch.yml`: comment header + `[]` (user patch layer, applied after every bundle layer)
  - `pnpm-workspace.yaml`: `packages: ['.']`, `nodeLinker: hoisted`, `autoInstallPeers: false` (out-of-tree plugins get a flat hoisted `node_modules`; missing peers fall through to the healed `$DSH_HOME/profiles/node_modules` fallback, so every plugin shares the installation's single cordis instance)
- The profile `package.json`'s `dsh.profile.bundles` array is the **ordered loader entry list** the tree is composed from (`profile-boot.ts`: "The tree is composed as patches: each bundle in package.json's dsh.profile.bundles, then cordis.patch.yml, then any --patch overlays").
- `dsh plugin --profile <name> <args>` is a **thin pnpm forwarder** run inside the profile dir (`dsh/packages/cli/src/plugin.ts`): `add` = `pnpm add` there (works with a local path). After exit 0, `reconcilePlugins` appends every added dependency whose `package.json` declares `dsh.bundle.patch` to `dsh.profile.bundles` (in declaration order); deps without a `dsh.bundle.patch` get a one-time warning and are **not** added as loader rows.
- **Dual-face plugin manifest** (`package.json`):
  - `dsh.bundle: { patch: "./cordis.patch.yml" }` → the host-side loader entry (a Cordis patch layer with the plugin's service rows). This is what makes the plugin a *loader entry* of the profile.
  - `dsh.client: { inject: [...], platform: 'web', immediately?, external? }` → the browser-facing module-table row, composed into `window.__DSH_BOOT__`; served by the web server under `/plugins/<id>/client.js` (combo URL `/plugins/??<ids>&rev=<rev>`). The registry serves the built `lib/client.js` — the package must be **built** (`pnpm build` in the plugin package) before a live `dsh web` will load its client half (client AGENTS.md, checklist item 5; missing bundle → `MissingClientBundleError`, "run `pnpm run build` before launch").
  - `inject` in `dsh.client` is **informational only** (preflight display / HMR diffing) — it does not sequence activation; Cordis service waits do. `external` declares non-baseline module-table requests. `immediately: true` = stage-one prefetch.
- `dsh web` startup (`dsh/packages/bundle/web-app/`):
  - `src/startup.ts` (plugin `web-startup`) parses the flag family `--host`, `--port`, `--trusted-host`, `--no-open` via commander into the `webStartup` service.
  - `cordis.patch.yml` (lines ~117–124): `webServer` config `host: !!js ctx.webStartup.host ?? '127.0.0.1'`, `port: !!js ctx.webStartup.port ?? 3080`, compression gzip. **Default GUI URL: `http://127.0.0.1:3080`** (the running GUI in this environment).
  - `src/index.ts` (plugin `web-app`) config: `openBrowser` default `true` (suppressed by `--no-open`; also suppressed on SSH launches), `printUrl` default `true` — the ready line is printed on activation.
- **Ready line is a tokenized, authenticated URL**: dsh's own web e2e (`dsh/apps/web/tests/smoke-real.e2e.ts`) asserts the ready URL matches `/^http:\/\/127\.0\.0\.1:\d+\/\?token=[A-Za-z0-9_-]+$/u`; a GET on it responds `303` and sets an auth cookie. So a browser test must `page.goto(readyUrl)` including the `?token=` — that is the login handoff (no separate login form in these tests). `apps/cli/tests/web-auth.e2e.ts` covers the token exchange explicitly.
- dsh's own web e2e style (`dsh/apps/web/tests/*.e2e.ts`, run via `vitest.web.config.ts`): **vitest + bare `playwright`** (`import { chromium } from 'playwright'`, `chromium.launch({ headless: true })`), not `@playwright/test`. They boot an **in-process** host with a temp harness home (`scaffold.ts`: `harnessHome = join(workspaceCwd, '.dsh-home')`, env `DSH_HOME`/`DSH_AGENTS_HOME` pinned) rather than spawning the CLI — but the CLI-spawning variant exists in `apps/cli/tests/web-auth.e2e.ts` (`node --import tsx <bin> web --no-open --port <port>` with a cleaned env that strips `KEY|SECRET|TOKEN|PASSWORD` names, plus `DSH_TELEMETRY_DISABLED: '1'`, `SSH_CONNECTION: ''`, `SSH_TTY: ''`).
- `dsh`'s own lockfile pins `playwright@1.61.1` (+ `playwright-core 1.61.1`) as dev deps for exactly these browser e2e lanes.

### How e2e-live installs the plugin into the test home

- **File naming note:** the brief's `tests/e2e-live.ts` / `tests/e2e-live-utils.ts` no longer exist (Item 1 above predates a rename). Current layout: launcher = `packages/dsh-model-settings/scripts/e2e-live.mjs`, fixture = `packages/dsh-model-settings/tests/e2e/dsh-fixture.ts`, test = `packages/dsh-model-settings/tests/e2e/server/model-settings.test.ts` (run via `pnpm test:e2e` → `vitest run --config vitest.e2e.config.ts`, include `tests/e2e/**/*.test.ts`). The original `scripts/e2e-live-checks.mjs` was deleted in commit `e74307a` ("convert live checks to a vitest e2e suite").
- **Temp home:** the launcher creates it with `root = mkdtempSync(join(tmpdir(), 'dsh-e2e-'))` (`scripts/e2e-live.mjs:37`) and pins it via `const env = { ...process.env, DSH_HOME: join(root, '.dsh'), DSH_AGENTS_HOME: join(root, '.agents') }` (line 38). The temp root is **also the child's cwd** (`spawn('dsh', ['web', '--port', String(port), '--no-open'], { cwd: root, env, ... })`, line 41), so nothing is shared with the real home. `resolveDshHome()` reads `$DSH_HOME` (precedence: configured path > `$DSH_HOME` > `~/.dsh`), and `resolveProfileDir('web')` → `<home>/profiles/web` = `<root>/.dsh/profiles/web` (`dsh/packages/boot/app-boot/src/profile.ts:127-134`).
- **How the plugin gets into the profile:** the launcher runs, **synchronously before boot** (line 39, `addPlugin(env)`), the CLI: `spawnSync('dsh', ['plugin', '--profile', 'web', 'add', PACKAGE_ROOT], { cwd: root, env, stdio: 'pipe' })` (lines 95-96), where `PACKAGE_ROOT = fileURLToPath(new URL('..', import.meta.url))` — the **absolute path** of the repo package. `dsh plugin` is a thin pnpm forwarder (`dsh/apps/cli/src/plugin.ts:120-138`): if `<profile>/package.json` is absent it calls `initProfile(dir, template?.bundles ?? DEFAULT_PROFILE_BUNDLES, ...)` (writing the template manifest, an empty `cordis.patch.yml`, and a `pnpm-workspace.yaml` with `nodeLinker: hoisted` / `autoInstallPeers: false`), then `spawnSync('pnpm', ['add', PACKAGE_ROOT], { cwd: profileDir })`. So it is **`pnpm add` of a local (absolute) directory path** — pnpm records it as a **link dependency** and symlinks the repo package into `<root>/.dsh/profiles/web/node_modules/@apkawa/dsh-model-settings` (no copy, no registry access, no build scripts run). Relative specs would be anchored to the invoking dir (`anchorPathSpec`, `plugin.ts:104-112`), but here the absolute path passes through untouched.
- **Template vs reconcile:** the template (`PROFILE_TEMPLATES.web`, `dsh/packages/boot/app-boot/src/profile.ts:142-145`) lists only `['@deepseek-ai/dsh-base', '@deepseek-ai/dsh-web-app']` — the plugin is **not** in the template. It is **appended after `pnpm add`** by `reconcilePlugins(before, dir)` (`plugin.ts:59-91`, called on exit 0 at line 149): every installed dependency that resolves to a package declaring `dsh.bundle.patch` in its `package.json` is pushed onto `dsh.profile.bundles`. The plugin's manifest declares `"dsh": { "bundle": { "patch": "./cordis.patch.yml" } }`, so `@apkawa/dsh-model-settings` joins the layer list as the third bundle.
- **How `dsh web` loads it:** boot (`dsh/apps/cli/src/profile-boot.ts` `runProfile`/`composeProfile`) calls `loadProfile`, which resolves each `dsh.profile.bundles` entry two-anchor (dsh installation first, profile dir second) and parses its `dsh.bundle.patch` file; layers are composed in order over an empty root config, then the profile/user/home patch layers. The plugin's `cordis.patch.yml` is just `insert: [{ id: model-settings, name: '@apkawa/dsh-model-settings' }]` — the Loader then imports the package's `main` (`lib/index.js`) through the profile `node_modules` symlink and registers the host plugin (the `/model-settings` RPC channel, settings watcher). The **client** half is picked up separately: the package's `"dsh": { "client": { inject: [...], platform: 'web' } }` + `exports["./client"]` (`lib/client.js`) joins the web module table (`dsh-client-modules`, serves the built bundle under `/plugins`); that is the browser-facing half and is irrelevant to the browserless RPC test but **required pre-built** for a real `dsh web` to serve the GUI.
- **Pre-built artifacts:** the launcher hard-fails before boot if artifacts are missing: `const missing = ['index.js', 'client.js'].filter((name) => !existsSync(join(PACKAGE_ROOT, 'lib', name)))` → `fail('built artifacts missing: … — run "pnpm build" in the package first')` (`e2e-live.mjs:34-35`). The **test never builds**; `pnpm build` (`tsc -p tsconfig.json && tsdown` in the package's `package.json` scripts) must already have been run by the developer. It also requires `dsh` and `pnpm` on PATH up front (`requireCommand('dsh', ['-V'])`, `requireCommand('pnpm', ['--version'])`, lines 31-32).
- **Env passed to the child:** `env = { ...process.env, DSH_HOME, DSH_AGENTS_HOME }` — i.e. **full inheritance** of the dev machine environment plus the two home pins. There is **no explicit API-key handling** (any `DEEPSEEK_API_KEY`/etc. in the dev env flows through; none is needed — see below) and **no explicit `DSH_TELEMETRY_DISABLED`** (inherited only if the dev set it; contrast dsh's own CLI-spawning tests, which strip `KEY|SECRET|TOKEN|PASSWORD` names and set `DSH_TELEMETRY_DISABLED: '1'`).
- **Ready-line wait:** `waitForReadyLine` scans the child's stdout/stderr for `/dsh web: (http:\/\/[^\s]+)/` with `READY_TIMEOUT_MS = 90_000`; on match it rewrites `://0.0.0.0` → `://127.0.0.1`, does `fetch(url)` and **requires HTTP 200** (line 47), then prints `dsh e2e instance: <url>` and `temp root: <root>`. The fixture (`tests/e2e/dsh-fixture.ts`) spawns `node scripts/e2e-live.mjs --port 3091` and polls its stdout for both lines (120 s deadline). SIGTERM to the launcher forwards SIGTERM to the child and `rmSync(root)` unless `--keep`.
- **Warm model seeding (no provider needed):** the test seeds a model by writing `<root>/.dsh/settings.yaml` directly (`warmModel`, fixture lines 95-119) with `baseURL: http://127.0.0.1:9/v1` — "any probe the host makes is refused locally and skipped quietly — **no internet involved**" — then polls `listModels` until the host's settings watcher commits it. The autofill test uses a local 127.0.0.1 JSON server as a llama.cpp stand-in. RPC is plain `POST /model-settings/<endpoint>` with body `{ type: 'client-request', rpcId, method, payload }`.
- **Network at test time (model-settings):** effectively **none** — `pnpm add` of a local directory is a link dep (no registry fetch); in-box bundles resolve from the dsh installation itself (two-anchor resolution, no profile install at boot — the 0.1.1-rc.2 spike home shows `<root>/.dsh/profiles/web/` with **no** `node_modules` and a 28 s cold boot that is plain boot time, and the only pnpm-spawning code in either version is `dsh plugin`); all probes/listings are loopback. Caveat: `pnpm add` still runs a real pnpm, so in this sandbox its store/cache must be project-writable (`pnpm_config_store_dir=./.cache/pnpm/v11`), otherwise it tries `~/.cache/pnpm` and the plugin-add step fails.
- **ddgs cross-check (`packages/dsh-web-search-ddgs`):** same mechanism, near-identical files. Differences: temp prefix `web-search-ddgs-e2e-`; build check only `['index.js']` (host-only plugin, no client half, `pnpm build` = `tsc` only); the fixture has **no RPC plumbing** (the plugin only registers a `web_search` provider, so the observable contract is boot + linkage + HTTP 200) and instead offers `pluginListed(handle)`, which re-runs `dsh plugin --profile web ls` in the temp home and checks stdout for `@apkawa/dsh-web-search-ddgs`; fixture ready timeout 180 s vs 120 s; two test files: `tests/e2e/server/boot.test.ts` (links plugin + HTTP 200) and `tests/e2e/server/live-search.test.ts`, which **does not use the launched dsh at all** — it constructs `DdgsSearchProvider` + `createRunner` directly against real `uv` and **real network**, self-skipping via `describe.skipIf(!uvAvailable)`. That is the only real-network part of either e2e lane.
- **Complications for reusing this for a NEW playwright test:**
  - The plugin-add step is **implicit** inside `scripts/e2e-live.mjs` (a `spawnSync` dsh CLI call, not something the test script controls) — best reused verbatim by spawning the launcher and parsing its ready/temp-root lines, exactly like `dsh-fixture.ts` does.
  - The launcher hardcodes `spawn('dsh', ...)` — **the `dsh` on PATH** (here 0.1.2-rc.1), while the planned baseline is 0.1.1-rc.2 (provisioned at `.tmp/dsh-versions/0.1.1-rc.2/node_modules/.bin/dsh`). Versions differ behaviorally: 0.1.2-rc.1 prints a **tokenized** ready URL (`?token=…`, GET → 303 cookie handoff; the launcher's 200 check passes because `fetch` follows the redirect), 0.1.1-rc.2 prints a plain URL (direct 200). A playwright `page.goto` must use the tokenized URL on 0.1.2+.
  - Fixed port `E2E_PORT = 3091` (launcher default 3081 collides with a running GUI); consider `--port 0` + parsing the printed URL, as dsh's own CLI-spawn tests do.
