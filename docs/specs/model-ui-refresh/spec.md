# Spec: model-ui-refresh

**Проблема.** При изменении моделей в стандартном интерфейсе dsh (или в файле
настроек напрямую) наш раздел «Model settings» не обновляется, хотя сам dsh
(страница Models) подцепляет изменения мгновенно. Раздел остаётся с прежним
списком моделей, пока не перезагрузить страницу.

## Корневая причина (по итогам research.md)

Клиентская половина плагина (`src/client/index.ts`) запрашивает список строк
один раз, при монтировании (`loadRows()`), и далее перечитывает его только
после собственных действий (`save`, `refreshContextWindow`). Никакой
подписки на внешние изменения нет.

Стандартная страница Models, напротив, подписывается на форвард-событие
`settings/document-updated` (`ctx.remote.$on(...)`), поэтому обновляется
мгновенно. Это событие хост шлёт при каждом изменении raw-секции — и после
коммита из UI, и после перезагрузки settings-файла (chokidar-вотчер
`settings-file`), с аргументами `(ns, revision)`.

## Решение

Клиентская половина подписывается на то же событие и при изменении нужной
секции тихо перечитывает строки:

1. **Подписка** (в `apply`, `src/client/index.ts`): через `ctx.get('remote')`
   (сервис `remote` предоставляет `dsh-api-gateway` и присутствует в том же
   web-скоупе) — `remote.$on('settings/document-updated', listener)`,
   оформлено `ctx.effect(...)` с disposer, как в `ui-settings-models`.
   В `export const inject` добавляется `'remote'` (как в `ui-settings-models`).
   `ns` сравнивается со строкой `'llm-pi-ai'` (hardcoded: клиентский бандл
   не импортирует хостовый код — то же правило, что у строки `CHANNEL`).
   Доступ к `remote` — структурный mirror по образцу `ConnectionHandle`,
   без новой peer-зависимости на `dsh-api-remotes`.
2. **Тихий рефреш** (в `ReasoningSectionController`): новый метод
   (типовая семантика — «рефреш по инвалидации»), который:
   - не переворачивает `phase` в `'loading'` (список не размонтируется, черновики
     строк не теряются);
   - при неудаче RPC сохраняет прежние строки (не переходит в `'error'` —
     фоновая инвалидация не должна срывать рабочий список);
   - имеет sequence-guard: ответ, пришедший после более позднего запроса,
     игнорируется (защита от out-of-order при конкурентных перечитываниях).
   Публичный `loadRows()` (Retry / первый загрузочный вызов) сохраняет
   текущее поведение с фазой `'loading'`.
3. **Перепринятие чистых черновиков** (в `ModelRow`, `ReasoningSection.tsx`):
   `useEffect` на `row.efforts` — если черновики не отличаются от сохранённых
   (`draftsDirty(drafts, row.efforts) === false`), заново инициализировать их из
   `row.efforts`. Защищает от затирания внешнего изменения: без этого
   незапятнанный черновик отличался бы от новых внешних efforts, и Save пометил
   бы строку «dirty», отправив устаревшую карту. Аналог уже существующего
   focus-aware sync для поля context window.

## Чего НЕТ в скоупе

- Подписки на `credentials/updated` / `llm/adapters-updated` — строки секции
  не зависят от них (хост читает только секцию `llm-pi-ai`).
- Обработка `connection/reset` — не работает и сейчас, отдельная история.
- Изменения хостовой половины: хост и так шлёт события и автозаполняет
  contextWindow; ему ничего не нужно.
- v1-карточка и EffortButton (за `CLIENT_ENABLED`) — не трогаем.

## Известные ограничения (после фикса)

- Если рефреш по инвалидации упал (RPC-ошибка), список остаётся прежним до
  следующего события; явного индикатора «данные могут быть не свежи» нет.
- В процессе сохранения/обновления (кнопка жата) внешнее изменение может
  перечитаться «под ногами» — последним словом будет ответ хоста, что
  допустимо (хост — источник правды).

## Критерии приёмки

1. В работающем `dsh web`: изменение списка моделей в стандартной странице
   Models (или правка settings-файла) → в разделе «Model settings» список
   строк меняется без перезагрузки страницы и без вспышки «Loading models…».
2. Черновики, введённые пользователем (level-карты, ctx-поле), не сбрасываются
   внешним рефрешом и не затирают внешнее изменение при последующем Save.
3. `pnpm typecheck` и `pnpm test` зелёные; новые тесты: тихий рефреш,
   sequence-guard, поведение при ошибке RPC.
